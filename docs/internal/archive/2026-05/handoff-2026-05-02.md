## Surprises this session

### Stage B was already shipped

The 2026-05-01 handoff (and the C# inspector source) said
`PS1SoundMacro` / `PS1SoundFamily` were "Phase 5 Stage A scaffolds —
runtime ignores them until Stage B ships." That's wrong:

- `psxsplash-main/src/soundmacro.{cpp,hh}` — full
  `SoundMacroSequencer`, frame-keyed event scheduler, per-macro
  cooldowns + voice caps, post-keyOn pitch shift via
  `MusicSequencer::pitchForOffset`.
- `psxsplash-main/src/soundfamily.{cpp,hh}` — full `SoundFamily`,
  uniform-random variant pick with anti-repeat, vol/pitch/pan jitter
  sampling, cooldowns.
- `scenemanager.cpp` lines 206-210 init both, lines 581-582 tick
  both per frame.
- `luaapi.cpp` lines 2391/2411 dispatch `Sound.PlayMacro` /
  `Sound.PlayFamily` through the sequencers.

Net result: I added the experimental badge inspector (`9c9b578`)
based on the stale wording, then reverted it (`2a2d79e`) and
rewrote the C# resource doc-comments to point at the actual runtime
entry points. **If you write new resources where the runtime really
hasn't shipped, recreate `PS1ExperimentalBadgeInspector.cs` from
the `9c9b578` git history** — the structure is fine, only the
switch's match cases were stale.

### `SetVisible` string-arg footgun is now patched

`Lua UI.SetVisible(string)` previously silently no-op'd because the
runtime only accepted numeric handles (memory note
`project_ui_findelement_signature`). The 2026-04-30 commit
`42bf90c` made the runtime forward strings to `setCanvasVisible`,
so the asymmetry is gone. Updated the demo Lua script to use the
explicit `UI.SetCanvasVisible` form anyway since it reads better.

### `ps1_default.tres` had a leaked editor binding

During the commit pass for C2 (BG bake quality), the dirty tree
included an `albedo_tex = res://demo/textures/grass.png` line on
the shared shader resource. That would have given every mesh using
`ps1_default` a default grass albedo. Reverted the .tres delta and
shipped C2 without it. If you actually wanted grass as a default
preview, re-apply the line; the revert assumed it was an inspector
accident.

## Open question — documentation strategy

We have a lot of docs (40+ markdown files under `docs/`, scattered
README files in `addons/`, the templates/README, the in-source
`///` doc-comments, the EmmyLua stubs, the Lua API cheatsheet
dock). They're written piecemeal as features land — there's no
single entry point for "I just installed PS1Godot, now what?" or
"how do I author my first scene?" or "what's the splashpack format?"

Things to think about before tomorrow's session:

1. **Audience.** Are we writing for:
    - **Yourself in 6 months** (current implicit audience — terse,
      assumes context, lots of cross-refs to architecture plans)?
    - **Other PS1 homebrew authors** (would want a stable Lua API
      reference, splashpack format spec, and a "build your first
      scene" tutorial)?
    - **Both, in different surfaces?**
2. **Format.** Pick one spine and let everything else hang off it:
    - **Single `README.md` at repo root** with a hand-curated
      reading order pointing at the existing detail docs. Cheapest;
      no new tooling.
    - **Static-site generator** (mkdocs / docusaurus / vitepress)
      consuming the existing markdown. Looks polished, gives search
      + nav for free, costs CI / build setup.
    - **Godot's built-in EditorHelp** — extend the tooltip plugin
      we shipped to also publish a class-help index that F1
      navigates to. Best author-experience integration; bigger
      lift, requires reverse-engineering Godot's class XML format.
3. **Lua API doc surface.** The cheatsheet dock is in-editor; the
   EmmyLua stubs feed external editors. Both are auto-generated
   from `luaapi.hh`'s `// Namespace.Method(args) -> ret` blocks.
   That format is the source of truth — should we lean into it?
   Tighten the comment-block conventions, add `@param` /
   `@returns` / `@see` tags, regenerate stubs + cheatsheet + a
   public Lua API reference page from one parser?
4. **Splashpack format.** `docs/splashpack-format.md` exists but
   was last updated for v25; we're at v32. Either auto-generate
   the format doc from the C# writer + C++ reader (hard, both
   sides drift) or budget a quarterly manual sync (cheap but rots).
5. **Architecture / "why" docs.** `ROADMAP.md`,
   `ps1-memory-strategy.md`, `ps1_asset_pipeline_plan.md`, etc.
   are author-facing-but-internal — strategy docs for ourselves.
   Keep these as-is, surface them through the spine, but don't
   restructure into something they're not.

A Phase-3-shaped task could be:

> **Phase 3 #29 — `docs/INDEX.md` + reading order.** Single
> markdown listing what each existing doc covers and the order
> someone new should read them. Half a day. Defers the bigger
> static-site / EditorHelp question until we know what's actually
> useful.

If the bigger move feels right, the next-tier task would be
porting that index into mkdocs/docusaurus + a CI publish step. But
the cheap MVP is the index page.

### CRLF line endings warning

Every C# edit triggers a `LF will be replaced by CRLF` git warning.
Benign — repo stores CRLF, my edits write LF, git auto-converts on
commit. Don't try to "fix" it; `core.autocrlf` is doing its job.

### `SplitContainer.SplitOffset` deprecated in Godot 4.7

Use `SplitOffsets = new[] { N }` (array, supports n-way splits).
Hit this in the cheatsheet dock; one-line fix.

### `Godot.FileAccess` vs `System.IO.FileAccess` ambiguity

`using Godot;` + `using System.IO;` clashes on `FileAccess`. Fully
qualify: `Godot.FileAccess.Open(resPath, Godot.FileAccess.ModeFlags.Read)`.

### `PS1Scene` is a Node3D, not a Resource

So `EmitChanged()` doesn't exist on it. Mutating its array
properties dirties the scene file via Godot's normal tracking;
`NotifyPropertyListChanged()` refreshes any open inspector. Ran
into this writing the .wav drop helper.

### Command-line cwd surprises after `cd`

The shell session persists working dir between Bash calls. Once I
ran `cd godot-ps1`, subsequent `cd godot-ps1` failed because I was
already inside it. Use absolute paths (`/d/.../godot-ps1`) or the
`-C` flag for git to avoid the trap.
