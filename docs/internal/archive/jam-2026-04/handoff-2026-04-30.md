# PS1Godot session handoff — 2026-04-30

Today's session built out the **fixed-camera prerendered-BG system** end
to end (Resident Evil / FFVII style) on top of the new `prerendered_demo`
scene, then surfaced a list of runtime bugs that block actually
*playing* it. Tomorrow's session is the bug-fix pass.

## TL;DR

What ships now:
- **`prerendered_demo.tscn`** — two rooms (tavern + storeroom) joined by
  a corridor, lit with two `OmniLight3D` colour rigs, dressed with 13
  Fab "Fantastic Village Pack" FBX props (table, chairs, shelf, barrels,
  brazier, treasure chest, crates, sacks). Every prop is wrapped in a
  new `PS1Backdrop` node that emits a per-mesh AABB collider but skips
  runtime render — props live in the BG image, not in PSX VRAM.
- **`PS1Backdrop` node + SceneCollector branch** (`PS1Backdrop.cs`,
  `SceneCollector.cs:444-460`, `EmitBackdrop` helper around line 3130)
- **16bpp BG textures** (FF9 standard, no palette banding) — set via
  `BitDepth = 2` on the bg_image PS1UIElements
- **Supersampled BG bake** — `BackgroundBaker` now renders at 4× target
  resolution with 8× MSAA and Lanczos-downsamples to 256×240. Anti-
  aliased silhouettes, captures wood-grain / brick detail
- **Player avatar excluded from BG bake** — `BackgroundBaker.HidePlayers`
  walks the scene before render, sets `Visible=false` on every
  `PS1Player`, restores after. Otherwise the live runtime-rendered
  avatar would composite on top of a frozen ghost twin
- **Per-mesh ShaderMaterial mute** — bake-time `modulate_scale=1`,
  `preview_quantize_bits=0`, `preview_dither=false` now applied to
  every per-mesh ShaderMaterial referencing ps1.gdshader, not just the
  shared `ps1_default.tres` singleton
- **Authored `PS1NavRegion` polygons** for RoomA / Corridor / RoomB with
  shared endpoint verts at the corridor mouths — exporter logs
  `Nav: stitched 4 portals across 3 regions`
- **`PerfOverlay` runtime HUD** — top-left semi-transparent black plate
  showing live FPS / frame time / tri count / object count / VRAM in KB.
  New `PSXSPLASH_PERFOVERLAY` build flag, default-on in both
  `build-psxsplash.cmd` and `build-psxsplash-cdrom.cmd`. Counters fed
  from Renderer (tris) / SceneManager (objects + vram) / main.cpp
  (FPS + frame time)
- **UI sortOrder → OT depth split** (`uisystem.cpp:472-490`) — canvases
  with `sortOrder >= 128` (i.e. backdrop layer) now insert at OT depth
  `OT_SIZE-4` so 3D content composites *over* them. Canvases with
  `sortOrder < 128` keep depth 0 (HUD on top, unchanged for
  `demo.tscn`'s 20/30 sortOrder HUD canvases). This was the root cause
  of "no player visible" — BG canvas at depth 0 was painting OVER the
  avatar
- **Avatar mesh** — low-poly capsule (8 radial × 3 rings ≈ 192 tris,
  down from 3456 when Godot's editor baked the default `radial=64`
  CapsuleMesh into an ArrayMesh). Avatar transform scaled 1.5× to
  ~2.25 m tall so it reads at PSX render scale
- **Layout pass** — table moved off the spawn-to-corridor centerline
  to the east wall, lantern removed (FBX origin behaviour was
  unreliable), barrels shuffled to the NW corner, `LampA` follows the
  new table position

## Bugs to fix tomorrow

User-reported:

1. **Can't transition to Room B** (the corridor-walk feels physically
   blocked). Likely related to bug #4 below — if the wall colliders
   project ~1 m of clearance, the corridor's 2 m authored width
   collapses to zero walkable lane.
2. **Player doesn't "stick" to the floor** — sounds like Y isn't being
   clamped to the nav-region floor each frame, or gravity is pulling
   below floor and not snapping back. Worth checking
   `scenemanager.cpp:755-833` — the gravity + nav-clamp branch only
   fires when `!freecam && m_navRegions.isLoaded()`. If `isLoaded()`
   returns false for some reason, no gravity, no floor snap.
3. **Can't get within ~1 m of walls** — wall colliders are emitted from
   `EmitCollisionFor` (`SceneCollector.cs:3037+`) using the mesh's
   world-space AABB with no padding. Wall thickness is 0.2 m, capsule
   radius 0.45 m — effective stop should be 0.55 m, not 1 m. Either
   (a) PSX collision system inflates colliders, (b) the player has a
   runtime-inflated radius (`m_playerRadius` from PS1Scene), or (c)
   FBX-prop collision AABBs are spilling out past the visible mesh
   silhouette. Bet money on (b) first — `PS1Scene.PlayerRadius` defaults
   to 0.3 but might be much wider in the runtime config.
4. **Collision feels off in general** — see #1, #3
5. **Capsule mesh too small in PCSX** — partially addressed today (1.5×
   scale, height 2.25 m), but worth verifying once the avatar actually
   appears. Could be pure render-distance / FOV issue at Camera A's
   ~9.5 m distance from spawn.

Plus things I noticed but couldn't validate end-to-end (build failed
mid-session, last visual confirmation predates the OT depth fix):

6. **Avatar visibility** — the OT depth fix landed but is unverified on
   PSX. If still hidden, check Renderer's per-frame render path —
   maybe the avatar's tris project to OT index 0 (very close to camera)
   and end up co-located with UI canvases in the LIFO chain.
7. **PerfOverlay tris stuck at 192** — expected if only the avatar
   renders (BG props are CollisionOnly, no tris). Watch the value when
   `Camera.SetMode("third")` is called manually to verify counter
   actually updates with workload.
8. **Lantern FBX import** rendered the prop at floor level instead of
   `Y=2.7`. Removed from scene today; if you want a hanging lantern
   back, manually inspect the FBX scale via Godot inspector and find
   what compensates the unit mismatch.

## Suggested investigation order

1. **Print the runtime player radius and the wall colliders' XZ ranges
   on the first frame** (one-shot `printf` in `scenemanager.cpp` after
   `loadScene`). Confirm or refute hypothesis #3-(b) in five minutes —
   if `m_playerRadius` is e.g. 1.0 you have your answer
2. **Toggle `Controls.SetEnabled(true)` ↔ `false` via Lua** to confirm
   the player is actually receiving input. If the avatar moves with
   controls disabled, something else is driving it
3. **Disable gravity** (set `Gravity = 0` on PS1Scene) to test whether
   the "not sticking to floor" symptom is gravity-overshoot vs.
   floor-Y-not-found. If the player floats at spawn Y, the floor query
   isn't returning a value
4. **Walk the splashpack hex** for the player avatar's offset bytes —
   verify the runtime is reading `playerAvatarOffset = (0, -0.25, 0)`
   in PSX coords, not garbage
5. **Last resort**: drop the wall meshes' `Collision = Static` to
   `None` and re-run. If the player can suddenly walk freely, the wall
   colliders are oversized. If they STILL can't reach Room B, the
   issue is in the corridor's nav-region or a portal-stitch bug

## Reminders / invariants

- **Don't `git add assets/village/`** without verifying the Fab
  "Fantastic Village Pack" license permits redistribution. Currently
  ~30 MB of FBX + base-color PNGs in the project tree
- **`PSXSPLASH_PERFOVERLAY` is now default-on in both build scripts** —
  if you ship a "release" build, drop the flag from
  `scripts/build-psxsplash*.cmd` so the entire overlay compiles out
- **OT depth threshold** for sortOrder is hardcoded to 128 in
  `uisystem.cpp`. If a HUD canvas needs sortOrder >= 128 in some
  future scene, this will silently route it to the BG layer. Consider
  exposing the threshold or using a flag bit instead
- **Avatar's `mat_avatar` StandardMaterial3D** has `texture_filter = 0`
  (nearest-neighbor) but no albedo_texture — runtime falls back to
  pure `albedo_color * vertex_color`. If you ever attach a face/skin
  texture, the avatar capsule's UVs are sphere-mapped and will look
  weird. Use a `PS1SkinnedMesh` instead for a proper character
